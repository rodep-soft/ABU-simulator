# 効率化戦略・Mustika直接受渡の実装結果

## 変更

- 初期選択をTR `adaptive`、BR `efficient` に変更。従来版は比較用に保持。
- 初便E3・次便E1+S2で開始する `adaptive-e3-e1s2` も追加。その後は必要量補給。Mustika準備・取得は開幕指定より優先。
- TRは未完成タワー、在庫、BRの手持ちから必要なEarth/Skyを選び、受け渡し容量を見込んで収集。常に3個集めることは強制しない。
- 条件達成が近ければTRがMustika前へ先行移動・待機。取得可否は実際の条件達成で判定。
- MustikaはTRが受け渡し位置で保持し、BRへ直接渡す。通常在庫の空き列は不要。床置き指示は拒否。物体が区画内、両者のアーム範囲内であることを確認し、作業時間を消費して保持者を一度だけ移す。
- BRは必要に応じて通常荷物を近場で配置し、空手にしてMustikaを受け取る。余ったSkyを使い切るためのEarthが不足する場合はTRが先に補給する。
- BRは受取後の見渡しを行い、Mustika奉納を優先。奉納後も通常作業を継続。
- BRの評価は最大2往復の点差・所要時間・実際に使う個数・持ち帰りを比較。有用な2個運搬を選びやすくし、必要なら短時間の補給待ちを挟む。Sky1個だけで完成する行動などは残す。
- TRはBRの受取側への接近中に積み増しを控える。実際に把持中の列にも積み増しをしない。
- BRの観測は見渡し時だけ更新。追加した味方情報はその時点の位置・手持ちであり、内部計画や未来の到着情報を通信しない。

同速・E3開幕の赤では、88.95秒の条件達成時点ですでにTRが初期柱前に待機していた。89.10秒に取得を判断し、90.65秒に取得した。ただしBRにSkyが残っており、Earthを受け取って近場にタワーを作り手持ちを解消する必要があったため、直接受渡は135.50秒になった。先回りで取得を早めても、BR側の準備時間は残ることを確認できる。

## 検証

- 自動テスト102件成功。従来戦略の検証も維持。
- 新規テストは満杯在庫での直接受渡、両色・ロボット配列順の入替、保持の一意性、得点の重複防止、区画外・異チーム・混載・条件未達の拒否、見渡しの更新制約を含む。
- E3がそろった状態で両色BRがE2を選び、1回の見渡し後に2個配置することを確認。
- 10試合の全3611保存フレームで全53物体の保存、二重保持なし、TR3/BR2上限、保持者の整合、車体活動域を確認。Mustikaが床在庫になるフレームは0。
- PC・スマホ幅の画面テスト成功。3倍速、戦略選択、直接受取、手持ち表示、満杯在庫表示、ログ出力、Retry、ファイル直接起動を確認。キャンバスは非空、横方向のはみ出しなし。

## 残る課題

- 見渡し停止の合計は必ずしも減っていない。補給を待って再認識する回数や、手持ち整理の往復はさらに調整できる。
- 同速・E3開幕では、TRがMustikaを持って受渡位置で待つ時間が39.50秒あった。床在庫の空き待ちではなく、BRの手持ち整理が主な原因。
- 相手の先着による配置失敗、Skyの取り合い、移動の詰まりは残る。これらの未来分岐はまだ全探索していない。
- 評価の時間・点差・個数・条件達成の重み、待機判断の期限は仮の方針。最適化済みの値ではない。
- Mustikaの直接受渡・床置きを使わない方針はユーザー指定として記録。転がり・落下の剛体物理や公式裁定の再確認は今回の実装範囲外。

`summary.csv`、`summary.json`、各試合の `*.audit.json` と `*.replay.json.gz` に結果を保存。再実行は `tools/audit-current-efficiency.cjs <未作成の出力先> --efficient`。元コードのハッシュと条件は `manifest.json` に保存している。
