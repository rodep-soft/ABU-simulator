# シミュレーションの競技仕様

更新: 2026-09-23。対象: 手元の `Robocon_2027_Rulebook_v1-1.pdf`。

この文書は、フィールド・動作・採点を実装するための基準案です。新しい [field-simulator.html](field-simulator.html) はこの基準で作成し、主要な制約を実装しています。物理・認識の簡略化と未対応事項は [README.md](README.md) に記録しています。旧アプリ・旧リプレイへ適用済みの仕様ではありません。戦術や初手の優劣はここでは決めません。

## 7. BRの認識と独立動作

公式にはBRは完全自動、TRとBRの試合中の通信は禁止（11.3、11.10）。固定場所での撮影停止は公式の義務ではなく、スライド4に基づく今回のロボットモデルの条件。

2026-09-23の確認で、BRは最大2個を一連の作業として配置してから戻る方式に決定。1個ごとの見渡し場所への帰還は要求しない。

通常の作業サイクル:

1. 見渡し場所へ到着し、完全停止して撮影・認識する。
2. 観測できた受け渡し在庫などから、次に受け取る最大2個を選ぶ。
3. 自陣の受け渡し区画へ行き、実在する物体を取得する。
4. ブロックを保持した状態で見渡し場所へ戻り、完全停止して再撮影する。
5. その時点の観測を使って、保持するブロックの配置先と順序を決める。
6. 最大2個を、出発前に決めた一連の計画に沿って配置する。
7. 配置終了後は見渡し場所へ戻る。ここでの認識が次サイクルの手順1を兼ねる。

初回も上陸後に認識してから受け取り計画を立てる。反転だけなどの空荷作業は、取得を省略できるが、外部状況に基づく判断には最後の観測を使う。

実装で保持する情報:

- **実際の世界**: 全ロボット、全物体、衝突、在庫、正しい点数。物理・ルール判定専用。
- **各ロボットの知識**: 最後に観測した時刻と内容、自分の積載、自分が実行した動作履歴。
- **各ロボットの計画**: 今実行中の作業と、最後の判断で決めた次の動作。

TRの納品予定、BRの配置予約、相手の未来行動を、別ロボットに共有する便利な変数として使わない。事前に決めた協調手順と、試合中の通信は区別する。TRが自動か手動かによる観測範囲も別設定にする。

BRが走行中に相手の操作で配置先を使えなくなった場合、エンジンは違法な配置や物体の上書きを防ぐ。ただし、その際に最新の盤面全体をBRへ渡して即座に最適化させない。検出できる局所的な障害で停止し、再観測へ戻る方式を実装案とする。再観測前に必要な障害検知の範囲は未確定。

見渡し時に盤面のどこまで見えるか、遮蔽、認識誤差、処理遅延は別のモデル設定。停止場所へ着いただけで全知の情報を取得できるとは限らない。

## 8. 時間・物理・同時進行

- 試合は180秒。終了時点で全ロボットと作業を停止し、終了後に配置完了イベントを適用しない（4.6）。
- 4台は同じ時刻軸で並行動作する。赤の処理を先にしただけで毎回赤が物体を取得する実装にしない。
- 同時取得は個体の把持状態と接触を解決してから1つの結果に確定する。未解決なら競合として停止・記録し、物体を複製しない。
- 最高速7 m/s、最高加速度3.5 m/s²を基準にする。速度倍率1、3/4、1/2、1/4は最高速・加速度の両方に掛ける（過去のユーザー指定）。
- 坂の速度係数、1段ごとの停止時間、把持・配置時間は調整可能な性能値とする。公式ルールの定数ではない。
- カメラの撮影・認識時間を車体の速度倍率だけで自動的に伸縮させない。既存の3秒は仮の参考値であり、実測や指定で更新する。
- 床・段差・柱・ロボット・ブロックに実際の外形を持たせる。目的地が同じ建設スポットでも、車体停止位置とアームによる物体の配置位置は別。
- 物体が安定する前、またはロボットが手を離す前に配置完了として得点しない。加算と反転は文字ログの内容でなく構造化した状態から判定する。

| OPEN-05 | Sky上面が混色・斜めのときの色判定閾値、安定の判定時間 | 「赤優先」「最後に触った方」などで決めない。判定保留の状態を持つ |
| OPEN-06 | 同一物体の再搬送点、終了時接触と既得運搬点の関係 | 8.1の永久保持と終了時接触条項を分けて記録。境界ケースは公式確認 |
| OPEN-07 | BRの初回上陸に坂を使えるか | 4.3.2はL1 Stairsへの進入に言及。初期モデルでは階段を使用 |
| OPEN-08 | 受け渡し区画の積み方・実効収容量、配置済み自Earthの回収先 | 無限在庫や場所を問わない回収を仮定しない。操作の詳細を詰める |
| OPEN-09 | 共有区画への進入口、フェンスの切れ目、正確な座標、段形状 | PPTは位置指定、公式図は寸法の根拠。STLと照合して境界を確定する |
| OPEN-10 | 坂・階段・認識・把持・配置・リトライに要する実時間 | 実機性能のパラメーターとして別管理する |
| OPEN-11 | 1個目の配置後に2個目の計画が成立しなくなったときの検出手段 | バッチ途中の全体再認識は自動では行わない。局所検知・安全停止・帰還のモデルを決める |
| OPEN-12 | 同点のL1/L2ブロック数における混成タワーの帰属、最終審判裁定 | 条文9.3に従う順序を保ち、曖昧な帰属で勝者を断定しない |

同点時の優先順は、Mustika奉納、自色Sky数、L2の有効ブロック数、L1の有効ブロック数、審判判断（9.3）。シミュレーターが再現できない審判判断は、乱数や固定のチーム優先で埋めない。

## 10. 既存アプリとの差分

調査対象は `app.js`、`tactical-replay.js`、`tools/action-space-catalog.js`。この表は確認できた主な差分であり、全コードの合法性を保証する監査ではない。

| 現状 | 新しい基準 |
| --- | --- |
| 赤青ともTR/BRの開始点の左右順がスライド1と逆 | 外側TR、内側BR |
| 受け渡し点が画像の中央寄りにあり、色付き正方形と不一致 | スライド2の正方形を面として扱う |
| 地上/L1の接続が短い横方向の線 | 実際の坂・階段の長手方向を通る |
| BRの見渡し点がL1下側寄り | スライド4の左右中央 |
| リプレイの通常作業は認識→取得→配置で、取得後の帰還・認識がない | 取得の前後で認識、最大2個の配置後に帰還 |
| 同じ高さ内の経路を直線で結ぶ箇所がある | 途中の地形とロボット外形も検査 |
| 行動辞書に相手専有スポットへの配置が列挙される | 活動域を満たす候補だけ合法として扱う |
| 行動辞書で「条件達成しそう」でもMustika取得候補が出る | 待機と取得を分け、取得時に実際の達成を検証 |
| リプレイのイベントがEarth層やSky色を書き換える | 個体・在庫・所有・接触・配置順を検証してから反映 |
| 手持ちや受け渡し在庫の負数を表示時に0へ丸める箇所がある | 負数の発生を状態不整合として検出・記録 |
| 未来の配送時刻や全体状態を使って筋書きを作る | 各ロボットが実際に利用できる情報から判断する |

この差分があるため、既存の戦術別到達時刻や得点は、今回の仕様に適合したシミュレーションの評価結果としては扱わない。

## 11. 実装の完了条件

最初の実装は、配置済みの正しいフィールドと、戦略を含まない動作検証を対象にする。順に、境界・経路、個体と受け渡し、配置と得点、BRの認識、4台同時進行を確かめる。

共通の判定器は、候補を生成する処理・画面操作・自動戦略・ログ再生から呼び出せる形にする。戦略が何を選んでも、違反動作や無効な状態更新を通さない。

ただし評価は1つの真偽値にまとめず、少なくとも「実行可能性」「ルール適合性」「得点の有効性」「認識条件の充足」を別々に返す。理由、条番号、関係するロボット・物体・時刻を記録する。

具体的な確認例は [RULE_CHECK_CASES.md](RULE_CHECK_CASES.md) にまとめる。全件が通るまでは、ルール準拠の全探索が完成したとは扱わない。
